# v3：底盘设计流程对照试验

轮次命名：按2026-10-20用户要求，本轮统一记为v3。原目录、冻结协议、源码和运行结果不变。

状态（2026-10-20）：18次开发测试、72次正式运行及全量轨迹核查已完成。正式有效方案数为M0 21/24、M1 23/24、M2 24/24。结果报告、原始记录和冻结材料保存于“流程对照试验运行_20261020”，与已有v2结果分开。正式冻结ID：65f43c4d1c37（完整哈希见freeze.json）。

## 1. 目的与分组

回答两个问题：整套方法能否提高有效设计方案的完成率；在工程工具相同的条件下，Agent组织任务是否改善需求适应性或减少流程开销。

| 组别 | 实施方式 | 比较用途 |
|---|---|---|
| M0：LLM直接设计 | 提供工程公式、适用范围及元件目录，允许多轮补问、解释和修改方案；不调用计算工具 | M2对M0为主要比较，评价整套辅助设计方法 |
| M1：固定工程工作流 | 同一LLM解析需求、补问并提出构型；程序按固定规则组织工程计算和报告 | M2对M1为补充比较，评价Agent组织任务的额外作用 |
| M2：Agent设计流程 | 同一LLM根据当前需求、审核与工具结果，选择下一步动作、计算模型及检查范围 | 本文方法 |

M1固定执行“需求整理/补问→输入校验→构型确认→载荷计算→全部允许候选匹配与检查→方案输出”；校验缺项时返回补问，需求变更后重新执行适用步骤，允许切换两类模型。不能把它设置为不会补问或不会处理变更的简单串行脚本。M1由程序调度，不是仅用一句prompt要求模型按序执行。

M1与M2使用相同工程函数、候选目录、已确认输入、反馈字段及审核规则。两者均可看到操作完成状态和实际检查范围；模型输入中均不提供程序生成的“下一步应调用哪个工具”建议。M0也获得相同的工程知识和用户事实；其缺少在线计算工具是系统层面的比较因素，因此M2对M0的差异不能单独归因于Agent决策。

## 2. 任务与数量

采用左右独立双HST、直行—转向双功率流两类构型，以履带式底盘为验证对象。

| 任务类 | 每类安排 | 评价重点 |
|---|---:|---|
| S1：完整需求的新方案设计 | 2类构型×2个不同工况组合＝4题 | 构型、参数匹配与工程有效性 |
| S2：需要澄清的新方案设计 | 每类构型各1题缺少关键参数、1题存在待澄清描述，共4题 | 补问后能否准确落实需求 |
| S3：已有合格方案的需求变更 | 每类构型各1题原方案仍可行、1题原方案失效但存在替代，共4题 | 变更适应性及重算开销 |

**正式试验：12题×3组×2次独立会话重复＝72次设计运行。** 另设6道开发题，每类任务、每类构型各1题，三组各运行一次，共18次联调；开发结果不并入正式结果。一次设计运行包含多次模型请求，72不是API调用次数。

12道正式题在确认输入后均存在可行方案，作为本轮“设计方案完成质量”的明确范围；已有无解试验可继续作为边界验证材料。每题均由离线参考计算确认可行性，再冻结；不得根据哪组表现较好来选择题目。

S3向三组提供相同的既有合格方案和变更要求，既有方案是公开的起始条件，不提供变更后的答案。这样无需以各组先前设计成功为条件筛选变更任务。正式题应更换负载、速度组合、接口条件及目录组合，不只替换措辞或单位；不复用v2题面或答案。

## 3. 评价指标

| 指标 | 统一判定 |
|---|---|
| **有效方案完成率（主指标）** | 提交可解析方案；准确采用已确认需求；构型与接口相符；所选元件在允许目录内；独立复算通过全部适用约束。任一不满足即未完成有效方案；不要求与参考方案选中同一组参数 |
| 需求落实率 | 按冻结的必要设计要求清单逐项核对最终输出，不按文字长短评分 |
| 变更一致性 | 仅对S3统计：最终方案及其计算依据是否采用全部最新要求 |
| 交互负担 | 补问轮次、重复确认次数；共同必需的审核节点单列，不算某组额外负担 |
| 流程开销 | 模型请求数、服务返回的token用量、候选×工况复算次数、端到端运行耗时 |

最终方案使用同一模板导出，评分器读取最终选择及其采用的输入，按统一单位与冻结公差独立复算；不补值、不替换候选，也不向被测组回传参考答案。程序内部“审核通过”不是最终评分依据。报告格式统一，避免把版式精美或篇幅长当成设计优势。

各组均统计全部安排的运行，包括未完成者；开销另列三组都成功的配对任务，避免把过早停止误判为高效。12道任务是比较单位，2次重复用于观察模型波动；先按题汇总，再报告组间差值及按任务成组重采样的95%区间，作为小规模探索性结果，不把重复会话当成新增任务。

优先展示一张“三组×任务类型”的有效方案完成表，以及一张交互与开销对照图。方案约束满足情况可支持工程有效性；没有实测数据时，不写底盘能耗或动力性能提升。脚本答复下的补问次数也不直接换算为工程师工时。

## 4. 执行安排

1. **开发联调**：用6道独立开发题检查输入解析、三组执行方式、统一输出与评分；三组享有同等的调试机会。
2. **冻结**：保存正式题、补问答复表、公式与目录、三组prompt、评分程序、模型配置的非敏感信息及源码哈希。所有组采用同一模型设置。
3. **统一预算**：每次最多36次模型请求、每次最多4096输出token、最多3轮补问；格式纠错和模型组织动作计入请求预算。网络失败最多原请求重试1次，也计入36次上限，并单列记录。三组均提供`continue_design`动作，用于保存中间推导并继续自检，不返回工程答案；M0不能因没有工具调用而被迫一次性提交。
4. **成组执行**：以“题号×重复号”为一组，在组内随机排列M0/M1/M2，串行运行，避免时段与并发差异集中在某一方法。每次运行启用新会话。
5. **统一答复**：使用冻结的工程师答复表，只回答已提出的问题，不额外提示下一步或计算答案；确认与变更信息对三组规则一致。此处是模拟交互，不称为真实工程师试用。
6. **汇总**：72次全部保留，按预设指标比较M2–M0与M2–M1。正式结果不用于反向修改本轮题目或prompt；后续开发调整另留记录。

若固定流程在标准任务上同样准确且更省调用，应直接报告；Agent是否具有额外优势由变更任务、交互量和实际开销共同判断，不预设每项指标都胜出。

## 5. Prompt与实现边界

系统提示词采用 `prompts/common.txt` 加对应组的 `M0.txt`、`M1.txt` 或 `M2.txt`。每轮任务消息使用 `prompts/task_message.txt`。其中占位符由运行器填入；本方案不展示正式参数题面与答案。

实现时增加：三组共用的方案导出接口、固定流程调度器、独立新题库及统一评分/成组调度。可复用现有工程函数与审核接口；**不能把现有 `development.scripted_agent` 直接作为M1，它读取私有目标输入，属于联调脚本。** M1调度器只能读取用户已提供、已答复的信息和实际工具结果；私有参考仅供实验后的评价使用。
