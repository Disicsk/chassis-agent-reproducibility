## 1. 本轮要测的改进

v3主要检查“能否找到可行方案”，Agent组已达24/24。v4检验更具体的设计能力：**在可行方案中落实工程师的选型偏好，并在连续需求变更时保留有效计算、合理保留或更换规格。**

新增Skill包含三条决策规则：先约束后偏好；根据变更影响复算；证据满足停止条件后结束搜索。共享补丁提供批量校核、当前条件下的候选比较及按依赖哈希复用计算。它们不改变液压模型，不预设优越结果。

## 2. 三组对照

| 组别 | 实施 | 回答的问题 |
|---|---|---|
| A 固定工程流程 | LLM解析与补问；程序执行全目录校核、相同缓存复用及公开偏好排序 | 合理的普通程序能达到什么水平 |
| B 通用Agent | 同一模型自主调用共享工具，给出任务目标但不加载专用Skill | 通用智能体的基准表现 |
| C Skill增强Agent | 与B相同，再加载底盘设计Skill | 专用流程知识能否带来额外收益 |

**主要比较C−B，次要比较C−A。** 三组获得相同工程公式、指标定义、候选目录、批量接口、缓存、答复和预算。A组具有相同的排序与复用能力；B组也明确知道设计目标。Skill不能包含正式题答案，工具不能为C组单独返回下一步指令。v3的旧结果不充当v4的新对照。

本轮评价Skill整体，不把效果单独归因于其中某一句提示。若需要模块贡献，后续再预注册消融，不从本轮挑选题目重跑。

## 3. 任务安排

继续采用两类履带式构型。每类情境为2类构型×2个新任务，共4题：

| 情境 | 任务结构 | 评价重点 |
|---|---|---|
| T1 选型取舍 | 初始设计后两次调整明确的选型优先级或最低裕量要求，保留原物理工况 | 是否按新偏好选择方案；是否避免重复工程计算 |
| T2 原方案可保留的变更 | 初始设计后两次局部工况修改，明确规格复用偏好 | 是否复查后保留合格原规格；是否只复算变化工况 |
| T3 需要替代方案的变更 | 初始设计后两次约束/目录联动修改，原方案至少一次失效 | 是否找到满足当前条件且符合偏好的替代；是否避免无依据换件 |

正式12题×3组×2次独立会话＝**72次设计运行**。每次包含初始设计与两次变更，按一个连续任务计，不把3个阶段当作独立样本。开发另设6题×3组＝18次。

T2/T3在任务开始时向三组提供相同的已知合格原方案；“规格变更数”始终相对这个公开基准计算，不能因为各组前一阶段选型不同而改变评分目标。原方案不包含后续变更答案。各阶段的用户要求及比较基准均预先确定，前一阶段失败不获得额外提示或参考选型；阶段间可保留自身记录，但不能借用其他组结果。

正式题根据预定物理条件和目录结构生成：有多个可行候选、取舍确实存在、包含宽裕与接近约束边界的工况；T2/T3覆盖局部及全局影响。不得按某组模型表现筛题。生成后检查与开发/v1—v3任务的输入重复情况，题面与答案只保存在本地private目录。

全部最终确认条件可行；无解处理沿用既有边界材料，不混入本轮成功率。阶段变更只在上一阶段完成或耗尽阶段预算后统一释放，不提前给后续信息。

## 4. 指标与判定

| 指标 | 判定 |
|---|---|
| **全程合格率（主要）** | 三阶段均满足当前硬约束及公开最低裕量，且采用正确的当前输入 |
| **偏好达成率（主要）** | 每阶段选型属于当前全部可行目录的公开字典序最优集合，允许并列；失败阶段计0，再按任务求均值 |
| 规格变更与相对裕量 | 报告规格位置变更数、压力/流量最小相对裕量、规格指数；按对应任务偏好解读，不把较大或较小一概说成优越 |
| 流程开销 | 每次任务模型请求、token、实际复算候选×工况数、缓存命中、补问与重复确认 |

数值质量由独立公式及独立排序实现复算；不能用模型自评或Skill自己的“完成”标志评分。最终报告的理由另做匿名语义审阅，不能以选型合格代替所有解释正确。

先按题汇总两次运行及各阶段，再进行配对比较和按题重采样区间。开销同时报告全部安排及共同合格任务；不能把提前失败的少计算当作高效率。不将API交互量换算成工程师工时。

压力/流量裕量仅反映既定模型，规格指数仅是目录归一化排量指标；没有实测或价格数据，不能写成动力性能、节能、降本、轻量化或制造优势。

## 5. 实施顺序

1. 已完成：编写Skill和共享补丁；用公开工程示例进行公式、排序、缓存及范围检查。这些是软件测试，不是LLM结果。
2. 接入v4独立运行器：固定流程调用`fixed_decision`，B/C可调用相同的`assess`和`compare_candidates`；每次运行独立创建缓存，不能跨组共享结果。
3. 使用6道独立开发任务联调三组。检查分组注入、当前输入审核、阶段释放、终止规则、独立评分、日志及请求预算。
4. 冻结正式题、共同工程说明、三组prompt、Skill、工具与评分源码。每阶段最多24次模型请求，每次最多4096输出token；每阶段最多2轮补问。格式纠正和最多1次网络重试均计入该阶段24次上限。
5. 按“任务×重复”成组随机排列三组，执行72次。各阶段失败仍记录并按统一规则进入后续阶段，初始公开参考方案仅在任务预定时提供，不能给失败组补发参考答案。
6. 汇总完整结果。达到哪项优势就写哪项；若A同样合格且开销更低，说明规则充分明确时固定程序的适用性。

- 所有组：`prompts/common.txt`＋共同工程公式＋Skill内`references/decision-contract.md`＋实际动作JSON规范＋当前公开任务及工具记录。
- A：再加`prompts/A_fixed.txt`；数值调度由程序执行。

Skill占用的token计入C组实际用量。默认每阶段共用最多24次请求，不能给C额外的重试或请求额度。共同工具允许一次完成数值检查，B组也可选择相同的候选范围；输出压缩规则三组一致。

本轮暂不安装为全局Skill，以便对照运行精确控制哪些组加载。不得将项目全目录或本实验方案作为被测模型上下文。
